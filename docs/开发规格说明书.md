## 0. 开始之前：六条硬约束

违反任何一条都会让设计失效，务必先读。

| # | 约束 | 原因 |
| --- | --- | --- |
| 1 | **只看 Windows 10 x64**。不做跨平台、不做多用户、不做云同步、不联网上报 | 个人本机自用项目，任何适配投入都是浪费 |
| 2 | **常驻内存合计 ≤ 100 MB**（主进程 + 所有 WebView2 子进程），空闲 CPU ≤ 0.5% | 这是项目的核心卖点。对标 NTQQ 客户端，必须低一个量级 |
| 3 | **一切视觉动效只在 CSS 层**。窗口尺寸/位置只在必要时变更一次，绝不逐帧改 | 逐帧改窗口尺寸会让 DWM 每帧重算背景模糊，必卡。这是全案最容易踩的坑 |
| 4 | **不写任何自动化**：不自动回复、不群发、不批量加好友、不自动同意请求 | 降低账号风控风险。`request.*` 事件只记日志 |
| 5 | **不修改、不注入、不 Hook QQ 客户端本体**，只与独立进程的 NapCat 通信 | 合规底线 |
| 6 | **数据只落本机**，无遥测、无统计 SDK；日志不记录消息正文 | 隐私 |

补充的第 7 条经验：**`calc()` 不能作为 `rgba()` 的 alpha 参数**——实测在 Edge/WebView2 上完全不生效，背景会整块透明。透明度与底色的动态计算一律在 JS/Rust 里算好，再写入 CSS 变量。

## 1. 项目概述

### 1.1 一句话

贴在 Windows 10 桌面上的一条 QQ 消息抽屉：收起是显示「谁：说了什么」的透明窄条，展开是就地生长的聊天窗口。**电脑上不登录 QQ 客户端**，消息来自本机跑的 NapCat（无头 QQ）。

### 1.2 数据链路

```
手机 QQ（保持在线）
      ▲▼ QQ 协议
   NapCat（无头 QQ，独立进程，暴露 OneBot 11 WebSocket :3001）
      ▲▼ ws + access_token
   qq-drawer.exe（Tauri 主进程）
      ├── ob 适配层：连接 / 事件解析 / action 封装
      ├── store 持久层：SQLite(WAL)
      ├── media 媒体层：图片下载 / 去重 / LRU
      ├── sched::notify 提醒决策（优先级纯函数）
      └── window 窗口层：几何 / 吸附 / 失焦 / 模糊 / 托盘 / 快捷键
      ▲▼ IPC
   WebView2：折叠条 / 面板 / 标签栏 / 消息列表 / 输入框
```

### 1.3 技术选型（已定，不要更换）

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 应用框架 | **Tauri 2** | 安装包 4–8 MB、常驻 30–80 MB。Electron 空闲就吃 150–250 MB，与目标直接冲突；WPF 做半透明圆角与动效成本高。窗口能力（透明/无边框/置顶/跳过任务栏/托盘/全局快捷键）全部原生支持 |
| 渲染层 | **WebView2**（Win10 内置运行时） | CSS 做半透明、圆角、动效、滚动最省力。代价是多进程内存，已计入预算 |
| 数据与逻辑 | **Rust** | 前端可能被重建/刷新，连接与状态不能挂在它上面。Rust 侧统一做幂等、落盘、优先级计算 |
| 前端 | **TypeScript + Vite + Solid.js** | 编译期细粒度更新、无虚拟 DOM diff，运行时约 7 KB，适合高频消息插入 |
| 存储 | **SQLite**（WAL） | 数千条消息用 JSON 文件会退化成全量读写 |
| 传输 | **OneBot 11 over WebSocket** | 需要双向：既收事件又发 action。Webhook 是单向的 |
| Win10 效果 | **`window-vibrancy::apply_blur`** + CSS 圆角 | 官方文档标注 `apply_acrylic` 在 Win10 v1903+ 拖动/缩放时性能很差；`DWMWA_WINDOW_CORNER_PREFERENCE` 是 Win11 专属，Win10 圆角只能在 CSS 层做 |

### 1.4 范围

**做**：QQ 私聊与群聊的收发、历史、图片、@、引用、撤回展示、本地静音、缓存管理。

**明确不做**（不要在实现中夹带）：

1. 微信（个人号不存在官方或稳定的"不登录就收发"途径，第三方 Hook 方案已被微信 4.0 后的密钥抹除机制封死）；
2. QQ 内置表情、表情包发送、QQ 秀、个性装扮、小程序、红包、文件传输、戳一戳、群签到、语音/视频通话；
3. 通知气泡式提醒形态、竖排折叠条、左右边缘吸附、未读数字红点、声音提醒、任务栏闪烁；
4. 读取或写入 QQ 自身的免打扰设置（技术不可行，见 §6.1）；
5. 多账号、多设备同步、云端归档；
6. 壁纸层嵌入（WorkerW / `SetParent`）——只做"始终置顶 / 不置顶"两档；
7. 任何自动化/机器人行为。

## 3. 界面与交互规格

### 3.1 形态总览

| 元素 | 尺寸 | 说明 |
| --- | --- | --- |
| 折叠条 | 高 40px，宽 180–420px（默认 264） | 自由摆放，可吸附上边缘；圆角 11px、0.5px 白色描边 |
| 抽屉面板 | 584 × 500 固定 | 以折叠条**左上角为锚点**就地展开；圆角 18px |
| 溢出层 | 面板内 `top:42px; bottom:0` | 覆盖消息区、不遮输入框；不改变窗口尺寸 |

窗口尺寸与形态一一对应：折叠 = 折叠条尺寸，展开 = 面板尺寸。两者切换时窗口尺寸**一次到位**，动画只做内容层。

### 3.2 折叠条

```
┌───────────────────────────────────────┐
│ ▍小陈： 今天几点到？                    │  40px 高，圆角 11px
└───────────────────────────────────────┘
  ↑2px 痕迹竖条  ↑会话名(次要色)  ↑内容(主要色，超长省略)
```

- 结构：`痕迹竖条(2px) + 会话名 + 冒号 + 内容`。**无头像、无图标、无未读数字。**
- 会话名固定宽度不参与省略；内容 `text-overflow: ellipsis`。
- **不做自适应宽度**——内容多长都不改窗口尺寸。这是刻意的：新消息永远不会触发窗口尺寸变化，也就不会触发 DWM 背景模糊重算。
- 拖动：按住任意位置拖动；位移 > 3px 判定为拖动（不触发展开），拖动后要抑制随后的 click。
- 右键：静音当前会话 / 设置 / 退出。

```
│ Enter 发送 · Ctrl+Enter 换行 · 粘贴图片作为 [图片] 发送 │
└────────────────────────────────────────────────────┘
```

**标签栏（42px）**

- 标签：高 26px、圆角 8px、字号 12px；选中态 8% 白底 + 描边。
- 未读标记：标签内左侧 2px 琥珀色竖条（**不是红点、不带数字**）。
- 静音标签：文字降第三级色 + `静音` 小徽标。
- `···` 固定最右，内部有未读时整体留轻微痕迹。
- 右侧按钮：`锁定`（可切换，激活时琥珀色）+ `▲`（收起）。
- 拖拽排序：按住横向拖动；顺序**不因新消息自动变化**。

**消息区**

- 内边距 `12px 14px 6px`；条目间距 9px（做在 `.row-wrap` 的 `padding-bottom` 上，**不要用父级 flex `gap`**——`gap` 不计入 `offsetHeight`，量出来的行高会系统性偏短，30 行就是 261px，虚拟滚动的坐标系与真实布局对不上，滚动条就会抽）；滚动条宽 6px、半透明白（必须自定义 `::-webkit-scrollbar`，系统默认样式会破坏透明观感）。
- 头像 26px 圆形；名字 11px 第三级色。
- 气泡：内边距 `7px 11px`、圆角 11px、最大宽 330px；自己发的右对齐淡蓝底，他人极低透明度白底。
- 连续同一人：后续消息缩进 34px（= 头像 26 + 间距 8），不再显示头像与名字。
- @我：琥珀色描边 + 气泡下方 `有人 @ 你`。
- 引用块：气泡内顶部一条竖线 + 被引用者名字 + 单行摘要，点击可跳原消息。
- 撤回：气泡 42% 不透明度 + 删除线 + 下方 `已撤回`。
- 图片：148×92 圆角缩略图，点击放大。
- 时间分隔：居中、11px、第四级色。

**输入区**

- 上边框 0.5px 弱分隔线；**`z-index` 要高于溢出层**，保证溢出层展开时仍可打字。
- 输入框圆角 9px、最小高 32px、最大高 88px（超出内部滚动）、字号 13px。
- 发送按钮高 32px、圆角 9px、**不做彩色高亮**，深底 + 弱描边与面板同调。
- 底部提示行 11px 第四级色。

**溢出层 `···`**

- 向下展开覆盖消息区，**不遮输入框**；背景用近乎不透明的深色（`rgba(28,28,27,.95)`），保证覆盖消息之上仍清晰。
- 每项：`痕迹竖条 + 会话名(固定96px) + 最后一条消息摘要(弹性) + 加入标签`。
- 点项 = 切到该会话并关闭；点「加入标签」= 插入标签栏并关闭；点面板其它区域 = 收回。

### 3.4 状态机

```
                 ┌──────────────┐
   启动/失焦/▲   │  COLLAPSED   │  折叠条可见
   ┌────────────►└──────┬───────┘
   │                    │ 点击折叠条
   │                    ▼
   │            ┌──────────────┐  动画 180ms：面板淡入 + 上移 6px
   │            │  EXPANDED    │  未锁定
   │            └───┬──────┬───┘
   │   失去焦点(点外部)│      │ 点「锁定」
   │            │      ▼
   │            │  ┌──────────────┐
   │            │  │LOCKED_EXPAND │  锁定常驻，点外部不收起
   │            │  └──────┬───────┘
   └────────────┴─────────┘  ▲ 或 再点「锁定」
```

| 状态 | 进入 | 退出 | 窗口尺寸 |
| --- | --- | --- | --- |
| `COLLAPSED` | 启动、失焦（未锁定）、点 `▲` | 点击折叠条 | 折叠条尺寸 |
| `EXPANDED` | 从 `COLLAPSED` 点击 | 失去焦点 / 点 `▲` | 面板尺寸 |
| `LOCKED_EXPAND` | 在 `EXPANDED` 点「锁定」 | 点 `▲` 或取消锁定 | 面板尺寸 |
| `DISCONNECTED` | WebSocket 断开 | 重连成功 | 保持当前 |

**关键规则**

1. 展开**不改变窗口位置**：锚点 = 折叠条左上角，面板向右下增长。
2. 越界时才做最小必要平移（最后一道保险，正常摆放不触发）。判定：`锚点 + 面板尺寸 > 工作区 - 16px`。
3. 尺寸切换与内容动画分离：窗口尺寸一次到位，动画只做 `opacity` 与 `translateY`。
4. `skipTaskbar` 后窗口也从 `Alt+Tab` 消失，**全局快捷键是必需品**。
5. 收起动作要幂等（已在折叠态时重复触发不产生副作用）。
6. 失焦可能是"用户点了托盘菜单"——加 300ms 的 `suppress_collapse_until` 抑制窗口，托盘交互前先设置它。

### 3.5 提醒与免打扰策略

**决策链**

```
消息到达
  │
  ├─ 是该会话正是当前查看的？ ── 是 → 直接追加，不闪、不留痕
  │
  ├─ 该会话在本地静音表里？ ── 是 → 静默入库 → 折叠条按优先级更新（不闪、不留痕）
  │
  └─ 非静音 → 折叠条闪烁 3 次 → 静止 → 留痕
                （若因优先级未能上折叠条，则改在对应标签 / ··· 上留痕）
```

**策略矩阵**

| 会话状态 | 位置 | 闪烁 | 留痕 | 折叠条内容 | 未读计数 |
| --- | --- | --- | --- | --- | --- |
| 非静音 | 非当前会话 | ✅ 3 次 | ✅ 轻微 | 抢占（优先级最高） | +1 |
| 非静音 | 当前会话 | ❌ | ❌ | 不抢占 | 0（即时已读） |
| 静音 | 非当前会话 | ❌ | ❌ | 仅在无未读非静音会话时显示 | +1 |
| 静音 | 当前会话 | ❌ | ❌ | — | 0 |
| 任意 | 在标签栏但非当前标签 | ❌ | ✅ 标签痕迹 | 按上述规则 | +1 |
| 任意 | 在 `···` 内 | ❌ | ✅ `···` 整体痕迹 | 按上述规则 | +1 |
| @我（非静音） | 任意 | ✅ | ✅ + @标记 | 抢占 | +1 |
| @我（静音） | 任意 | ❌（尊重静音承诺） | ❌ | 不抢占 | +1，展开后 @ 高亮保留 |

**痕迹定义**：会话名与内容提到第二/第一级色 + 内容字重 500 + 左侧 2px 琥珀色竖条。
**不是**红点、**不是**数字、**不是**常亮圆点、不做跑马灯。
清除条件：点击折叠条、展开面板、进入该会话、右键标记已读、程序重启。

**闪烁实现约束（关键）**

- **只改折叠条自身的 CSS 变量**（`background-color` 的 alpha 与 `border-color`），属于内容重绘。
- **绝对禁止**在闪烁中调整窗口 alpha / 分层窗口属性 / 调用 `apply_blur`——那是窗口级合成，每闪一次都会重算 DWM 背景模糊，必然掉帧。
- 节奏：亮 300ms → 暗 300ms，共 3 个周期（约 1.8s），`ease-in-out`。
- 闪烁期间不改窗口尺寸、不改布局；用户碰一下折叠条或面板立即停止并清痕。

### 3.7 透明度模型

三层各自独立、互不联动：

```
① DWM 层（窗口背后）
   Win10 → apply_blur（不用 apply_acrylic）
   只在设置变更或尺寸变化时调用，绝不在动画中调用

② 面板层（CSS 变量 --panel-a / --bar-bg）
   三档预设 + 滑杆连续调节；**展开态与收起态是两个独立的旋钮**
   · --panel-a  → 展开后的面板底板（默认 0.72）
   · bar_alpha  → 收起态的折叠条底板（默认 0.72，与面板一致）
   两者互不联动：收起条常驻桌面、面板只在需要时出现，对透明度的诉求本来就不同。
   折叠条走**同一套**可读性补偿公式，只是代入自己的 alpha。

③ 气泡层（CSS 变量 --bub-a）
   固定较低值（默认 0.35），不跟随面板档位
```

**三档预设**：清晰 0.90（浅色/花哨壁纸）｜ 半透 0.72（默认）｜ 通透 0.45（深色简洁壁纸）。
调节方式：设置面板滑杆、`Ctrl+滚轮`。

**可读性补偿（关键规则）**：面板 + 气泡两层半透明叠乘、背后壁纸明暗不定，文字对比度会失控。规则是**面板越透，底色压得越深**，而不是单纯变透明。

```
k = clamp((alpha - 0.30) / 0.60, 0, 1)        // alpha 越小，k 越小
panel-rgb = (26 + 18k, 26 + 18k, 25 + 17k)    // 越透 → 越接近 (26,26,25)
```

**边界约束**：气泡 alpha 低于 0.2 时**必须**依赖 0.5px 描边维持边界，否则相邻气泡会糊成一片。
（已验证：浅色壁纸 + 0.72 面板下实测面板 `rgb(91,90,87)` 对文字 `rgb(211,209,199)`，对比度约 4.5:1，满足 AA。）

### 3.8 动效

| 场景 | 时长 | 属性 | 约束 |
| --- | --- | --- | --- |
| 展开 | 180ms `ease` | 内容 `opacity 0→1` + `translateY(6px→0)` | 窗口尺寸一次到位，不逐帧 resize |
| 收起 | 160ms `ease` | 内容 `opacity 1→0` | 同上 |
| 提醒闪烁 | 600ms × 3 `ease-in-out` | 折叠条 `background-color` / `border-color` | 只在 CSS 层，不碰窗口 |
| 痕迹出现 | 180ms `ease` | `font-weight` / `color` / 竖条背景 | 不做位移 |
| 溢出层展开 | 140ms `ease` | `opacity` + `translateY(-4px)` | 不改变窗口尺寸 |
| 标签切换 | 120ms `ease` | 背景与描边 | — |

**统一原则**：动效只做 `opacity` / `transform` / `background-color` / `border-color`，**不做 `width` / `height` / `top` / `left` 的逐帧动画**。尊重 `prefers-reduced-motion`（`reduce` 时时长压到 0）。

## 4. 技术实现

### 4.1 架构分层原则

| 原则 | 说明 |
| --- | --- |
| 单一数据源 | 只有 Rust 侧的 SQLite 是权威数据；前端不缓存业务状态，只渲染 Rust 推来的快照与增量 |
| 协议隔离 | OneBot 的一切（事件名、字段、消息段格式）只出现在 `ob` 模块内，上层只认自己的规范模型。协议升级只改这一层 |
| 窗口与内容解耦 | 窗口的尺寸/位置/效果由 Rust 掌握，前端只画内容，**永远不直接改窗口几何** |
| 动画不上窗口 | 一切视觉动效在 CSS 层完成；窗口几何与 DWM 效果只在必要时变更一次 |

**Rust 模块职责**

| 模块 | 职责 | 关键点 |

> `visible:false` 先隐藏，等读完配置、定位好位置、应用完模糊效果再 `show()`，避免启动时"跳一下"。

**尺寸与锚点**

```rust
// 锚点 = 窗口左上角。展开/收起只改尺寸，不改位置。
const BAR_H: u32 = 40;
const PANEL: (u32, u32) = (584, 500);

fn apply_geometry(win: &WebviewWindow, expanded: bool, anchor: (i32, i32), work: Rect, bar_w: u32) {
    let (w, h) = if expanded { PANEL } else { (bar_w, BAR_H) };
    // 越界才做最小必要平移（FR-05）
    let mut x = anchor.0;
    let mut y = anchor.1;
    if x + w as i32 > work.right - 16 { x = (work.right - w as i32 - 16).max(work.left + 16); }
    if y + h as i32 > work.bottom - 16 { y = (work.bottom - h as i32 - 16).max(work.top + 16); }
    win.set_size(PhysicalSize::new(w, h)).ok();
    win.set_position(PhysicalPosition::new(x, y)).ok();
}
```

规则：① 尺寸与位置在同一次调用序列里设置，避免中间态闪烁；② 尺寸变化后**不要**立即重设模糊效果；③ 拖动结束（`mouseup`）判断上边缘吸附：`y - work.top <= 20` 则吸到 `work.top`；④ 多屏用 `available_monitors()` 取目标显示器工作区，吸附与越界判定基于**当前所在显示器**。

**两条硬约束（都被真实 bug 咬过，别破）**：

- ⑤ **窗口形态只能有一个权威**。`expanded` 曾经有两份副本——Rust 的（决定窗口多大）和前端 store 的（决定画折叠条还是面板）。两份一旦错开，界面就卡在"展开尺寸的窗口里画着折叠条"，必须再点一下才恢复。现在 `set_expanded` 落完几何就广播 `window_state`，前端**只跟随**；另有 `window_state` 命令供前端启动自检。前端 `openPanel` 撑窗口失败时**绝不能**自己切成展开态，要回头读权威值。
- ⑥ **拖动窗口必须走 `begin_drag`，不能直接 `startDragging()`**。拖动会让窗口失焦，而未锁定时"失焦 = 自动收起"；于是拖到一半窗口被从展开缩成折叠，系统模态移动循环随后又把窗口矩形还原成拖动开始时的大小 —— 结果就是"展开尺寸 + 折叠内容"。`begin_drag` 先 `suppress_auto_collapse`，折叠态的 `Moved` 还会持续续期，覆盖整段拖动。

**失焦收起**

```rust
win.on_window_event(move |e| {
    if let WindowEvent::Focused(false) = e {
        if !locked.load(Ordering::Relaxed) && Instant::now() > suppress_until.load(Ordering::Relaxed) {
            let _ = win.emit("auto_collapse", ());   // 先发事件让 UI 淡出，不要同步写库
        }
    }
});
```

**模糊效果**

```rust
#[cfg(target_os = "windows")]
fn init_effect(win: &WebviewWindow) {
    // Win10 用 apply_blur。不要用 apply_acrylic —— 官方文档标注其在 Win10 v1903+
    // 拖动与缩放时性能很差，而本项目的窗口会被频繁拖动。
    let _ = window_vibrancy::apply_blur(win, Some((28, 28, 27, 180)));
}
```

补充：`DWMWA_WINDOW_CORNER_PREFERENCE` 是 Win11 专属，Win10 调用无效 → 圆角一律 CSS。Win10 亚克力在窗口失焦时会变成不透明深色，本项目失焦即收起，影响可忽略，但不要依赖"失焦时的模糊外观"做设计。

### 4.4 数据模型

**存储位置**

| 项 | 值 |
| --- | --- |
| 数据库 | `%LOCALAPPDATA%\qq-drawer\data.db`（`journal_mode=WAL`、`synchronous=NORMAL`、`foreign_keys=ON`） |
| 媒体 | `%LOCALAPPDATA%\qq-drawer\media\<sha256[0:2]>\<sha256>.<ext>` |
| 日志 | `%LOCALAPPDATA%\qq-drawer\logs\qq-drawer-YYYYMMDD.log`（环形，保留 7 天） |

> **本库是消息的唯一长期副本。** NapCat 侧只保留约 5000 条、文件标识同样受 LRU 管理，一旦被清理远端无从回查。因此本库不是"缓存"，清理 = 永久丢失。

**表结构**

```sql
-- 会话
CREATE TABLE IF NOT EXISTS conversation (
    peer_type       INTEGER NOT NULL,          -- 0=私聊 1=群聊
    peer_id         INTEGER NOT NULL,          -- user_id 或 group_id
    name            TEXT    NOT NULL,          -- 展示名：备注 > 群名片 > 昵称/群名
    raw_name        TEXT,
    remark          TEXT,
    last_msg_time   INTEGER,
    last_msg_text   TEXT,                      -- 折叠条预览（已单行化与截断）
    last_msg_sender TEXT,
    unread_count    INTEGER NOT NULL DEFAULT 0,-- 静音会话也计
    has_mention     INTEGER NOT NULL DEFAULT 0,
    tab_order       INTEGER,                   -- NULL=不在标签栏
    is_manual_tab   INTEGER NOT NULL DEFAULT 0,-- 手动加入（不被自动挤掉）
    updated_at      INTEGER NOT NULL,
    PRIMARY KEY (peer_type, peer_id)
);
CREATE INDEX IF NOT EXISTS idx_conv_recent ON conversation(last_msg_time DESC);
CREATE INDEX IF NOT EXISTS idx_conv_tab    ON conversation(tab_order) WHERE tab_order IS NOT NULL;

-- 消息
CREATE TABLE IF NOT EXISTS message (
    message_id      TEXT PRIMARY KEY,          -- 上游 message_id 的字符串形式
    peer_type       INTEGER NOT NULL,
    peer_id         INTEGER NOT NULL,
    seq             INTEGER,                   -- 会话内自增序号，稳定排序用（本地生成）
    ts              INTEGER NOT NULL,
    sender_id       INTEGER NOT NULL,
    sender_name     TEXT,                      -- 群名片 > 昵称
    is_self         INTEGER NOT NULL DEFAULT 0,
    text            TEXT,                      -- 纯文本合并结果（搜索与折叠条预览用）
    segments        TEXT NOT NULL,             -- 原始消息段 JSON（渲染依据）
    seg_types       TEXT NOT NULL,             -- 如 "text,image,at"
    reply_to        TEXT,
    is_at_me        INTEGER NOT NULL DEFAULT 0,
    has_image       INTEGER NOT NULL DEFAULT 0,
    image_state     INTEGER NOT NULL DEFAULT 0,-- 0=无 1=已落盘 2=下载中 3=失败 4=已清理
    is_recalled     INTEGER NOT NULL DEFAULT 0,
    recalled_by     INTEGER,                   -- operator_id
    recalled_at     INTEGER,
    send_state      INTEGER NOT NULL DEFAULT 0,-- 0=已确认 1=发送中 2=失败 3=本地乐观条目
    created_at      INTEGER NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_msg_id       ON message(message_id);
CREATE INDEX        IF NOT EXISTS idx_msg_peer_time ON message(peer_type, peer_id, ts DESC);
CREATE INDEX        IF NOT EXISTS idx_msg_atme      ON message(peer_type, peer_id, is_at_me) WHERE is_at_me = 1;

-- 图片索引（同时是 LRU 依据）
CREATE TABLE IF NOT EXISTS image_cache (
    sha256          TEXT PRIMARY KEY,
    rel_path        TEXT NOT NULL,             -- media/<ab>/<sha256>.<ext>
    ext             TEXT NOT NULL,
    bytes           INTEGER NOT NULL,
    width           INTEGER,
    height          INTEGER,
    sub_type        INTEGER NOT NULL DEFAULT 0,-- 0=普通图 1=表情包 2=QQ 表情图
    ref_count       INTEGER NOT NULL DEFAULT 0,
    created_at      INTEGER NOT NULL,
    last_access_at  INTEGER NOT NULL           -- 渲染时更新
);
CREATE INDEX IF NOT EXISTS idx_img_lru ON image_cache(last_access_at);

-- 群成员（@ 选人与名字解析）
CREATE TABLE IF NOT EXISTS member_cache (
    group_id    INTEGER NOT NULL,
    user_id     INTEGER NOT NULL,
    nickname    TEXT,
    card        TEXT,
    role        TEXT,
    updated_at  INTEGER NOT NULL,
    PRIMARY KEY (group_id, user_id)
);

-- 本地静音表
CREATE TABLE IF NOT EXISTS mute (
    peer_type  INTEGER NOT NULL,
    peer_id    INTEGER NOT NULL,
    muted_at   INTEGER NOT NULL,
    reason     TEXT,
    PRIMARY KEY (peer_type, peer_id)
);

-- 墓碑（手动删除记录）
CREATE TABLE IF NOT EXISTS tombstone (
    message_id  TEXT PRIMARY KEY,
    peer_type   INTEGER NOT NULL,
    peer_id     INTEGER NOT NULL,
    deleted_at  INTEGER NOT NULL,
    note        TEXT
);

-- 配置
CREATE TABLE IF NOT EXISTS settings (
    key    TEXT PRIMARY KEY,
    value  TEXT NOT NULL,                      -- JSON 编码
    updated_at INTEGER NOT NULL
);

-- 元信息
CREATE TABLE IF NOT EXISTS meta (key TEXT PRIMARY KEY, value TEXT);
-- 关键键：schema_version / self_id / last_connect_ok / napcat_version
```

**幂等约束**：`message_id` 是主键，写入统一走 `INSERT ... ON CONFLICT(message_id) DO UPDATE`，因此"同一 message_id 被事件与历史拉取各送一次"不会产生重复。

**墓碑的必需性**：若只从 `message` 表删行，下次向上翻历史或重启后远端补齐时 NapCat 会把这条消息原样送回来（"删了又出现"）。所有读取路径（本地查询、远端补齐、引用解析）都必须按 `tombstone.message_id` 过滤。

**数据生命周期**

| 数据 | 保留策略 |
| --- | --- |
| `message` | 永久保留（除非用户手动删除该条或清空会话） |
| 图片文件 | 默认 30 天 / 上限 2 GB，LRU（可配置；清理 = 永久丢失） |
| `tombstone` | 永久保留 |
| `member_cache` | 24h 过期刷新 |
| 日志 | 7 天环形 |

```
缓存清理（启动时 + 每 6h）：
 1) 按 last_access_at 淘汰超过保留天数的条目
 2) 若总量超上限，按 LRU 继续淘汰至低于上限
 3) 删除物理文件 + 删除 image_cache 行
 4) 把引用该图的消息 image_state 置 4（已清理）
 5) 写日志：删除条数、释放字节数
```

**不存在"自动删除旧消息"**——那会让历史出现空洞。占空间的主要是图片，所以只对图片做 LRU。

| OneBot 事件 | 本项目处理 |
| --- | --- |
| `meta_event.lifecycle.connect` | 记录 `self_id`，触发一次会话列表同步；置连接状态为已连接 |
| `meta_event.heartbeat` | 刷新最后活跃时间；连续 N 次丢失 → 判定断线 |

| `message_sent.group.normal` | 同上（群） |

**掉线语义**：NapCat 的事件是**一次性推送**。断线期间发生的一切（包括撤回）永久丢失，本地不会自动发现。这是产品层面的已知限制，不是 Bug。

### 4.7 消息段映射

**接收（渲染）**

| 段类型 | 关键字段 | 渲染 |
| --- | --- | --- |
| `text` | `text` | 正文；自动识别 URL 可点击（可选） |
| `image` | `file`, `url`, `sub_type` | 缩略图，点击看原图；`sub_type=1/2`（表情/贴纸）同样按图片渲染；落盘失败显示 `[图片加载失败]` |
| `at` | `qq` | `@昵称` 琥珀色令牌；`qq == self_id` 时整条标记 `is_at_me` 并高亮气泡 |
| `reply` | `id` | 引用块：竖线 + 被引用者 + 单行摘要；被引用消息已删除时显示「引用的消息已被删除」 |
| `face` | `id` | `[表情]` 纯文字占位（**不做图片**） |
| `mface` | `emoji_id` | `[表情]` 占位 |
| `record` / `video` / `file` | — | `[语音]` / `[视频]` / `[文件]` |
| `json` / `xml` | — | `[卡片消息]`（不解析小程序） |
| `forward` / `node` | `id` | `[合并转发]`（不展开） |
| `markdown` | `content` | **QQ 机器人的富文本**（实测：群机器人几乎只用它发图）。拆出 `![alt](url)` 当普通图片段下载落盘；`[文本](mqqapi://…)` 只留标签文字；其余字面量降级为普通文本。同一条消息里已有等价 `text` / `at` 段时不重复渲染（NapCat 会给纯文本 markdown 再补一份 `text`）。拆不出任何东西才退回 `[卡片消息]` |
| `poke` | — | 忽略 |
| 其它未知 | — | `[暂不支持的消息类型]`，**原始 JSON 入库**以便日后补渲染 |

**发送（输入层 → 消息段）**

| 输入层令牌 | 序列化结果 |
| --- | --- |
| 纯文本片段 | `{"type":"text","data":{"text":"..."}}` |
| `@某人` | `{"type":"at","data":{"qq":"<user_id>"}}`（群聊专用，不做 `at all`） |
| `[图片]` | `{"type":"image","data":{"file":"<本地缓存绝对路径>"}}` |

发送前校验：空内容不发送；纯空白不发送；仅有令牌无文本时按"图片消息"正常发送；私聊不允许 `at` 令牌。

### 4.8 关键算法与实现要点

| # | 要点 | 做法 |
| --- | --- | --- |
| 1 | **幂等** | `message.message_id` 唯一；自己发的消息先本地生成临时 id，收到 `message_sent.*` 时按 `message_id` upsert |
| 2 | **虚拟滚动** | 只渲染可视区 ±10 条；累计高度表定位；**视口位置只由锚点派生**——`offsets` 每换代一次（行高测量回填 / 翻页插入历史），都先取锚点（行 id + 行内偏移）再反算 `scrollTop`，**不做任何增量加减**（增量里混着测量、图片撑开、占位高度变化等无关项，补出来的位置是错的）；未测行的高度估值取已测行高的**中位数**，并且**只学一次**——首屏样本够了就钉死，换会话才重学（估值参与 `padTop` / `padBottom` 计算，跟着样本浮动的话**所有未渲染行**会一起变，500 行列表里就是几千像素的 `scrollHeight` 突变）；行对象必须**复用引用**（`core/grouping.ts` 的 `createRowCache`），因为 `<For>` 按引用 diff |
| 3 | **受控输入层** | 内部模型 = `Array<TextSegment \| AtToken \| ImageToken>`；渲染为 `contenteditable` 内的 span；令牌整体删除；发送时序列化为消息段 |
| 4 | **@ 选人** | 输入 `@` 触发弹层；成员来自 `get_group_member_list`（本地缓存 24h 或手动刷新）；只做搜索过滤，**不显示头像** |
| 5 | **粘贴图片** | 监听 `paste`，从 `clipboardData.items` 找 `image/*` → Blob 写临时文件 → 插入 `[图片]` 令牌；发送时用本地路径 |
| 6 | **图片落盘** | 收到图片段立即入队下载；`sha256` 命名去重；写 `image_cache`；渲染读本地文件，绝不请求外链 |
| 7 | **重连补齐** | 重连成功 → 拉 `get_recent_contact` 更新会话列表 → 对"当前打开的会话"补最后一页；不做全量补偿（NapCat 也没有） |
| 8 | **掉线提示** | 折叠条切换为 `连接已断开 · 点击重试`；日志记录断开原因与重试次数 |
| 9 | **撤回处理** | 按 `message_id` 标记 `is_recalled`；`operator_id != user_id` 时记录"谁撤了谁的" |
| 10 | **墓碑删除** | 写 `tombstone`；渲染与远端补齐统一过滤；同时删除对应图片文件 |
| 11 | **缓存清理** | 后台任务（启动时 + 每 6h）：按 `last_access_at` 与总量做 LRU；清理后 `image_path` 置空，前端渲染占位 |
| 12 | **权限最小化** | Tauri capability 只开放：自身数据目录读写、剪贴板读取、窗口几何与效果、托盘、全局快捷键；**不开放 shell、不开放任意路径读写** |

**剪贴板图片的真实边界**：Win+Shift+S 截图、PrtScn 走 `clipboardData` 能直接拿到 `image/png`，零依赖。但**从浏览器右键"复制图片"、从 Word/PPT 复制图片**这两类，剪贴板里往往根本没有图片数据（只有 `text/html` 或 `text/uri-list`）。MVP 只做"剪贴板里真有图片就发"，其余提示「剪贴板里没有图片」。

### 4.9 性能预算与优化清单

**测量口径（先看这条）**：WebView2 是多进程的，任务管理器里会同时出现 `qq-drawer.exe` 和多个 `msedgewebview2.exe`。只统计主进程会严重低估。

```
抽屉常驻内存 = 所有 qq-drawer.exe + 所有属于本应用的 msedgewebview2.exe 的内存合计
```

对比官方客户端时同样要把**所有** QQ 相关进程加总。

| 编号 | 指标 | 目标 | 上限 |
| --- | --- | --- | --- |
| PERF-01 | 安装包体积 | ≤ 10 MB | 15 MB |
| PERF-02 | 主进程常驻内存 | ≤ 25 MB | 35 MB |
| PERF-03 | WebView2 子进程合计 | ≤ 75 MB | 100 MB |
| PERF-04 | **常驻内存合计** | **≤ 100 MB** | 130 MB |
| PERF-05 | 空闲 CPU（60s 平均） | ≤ 0.5% | 1.0% |
| PERF-06 | 冷启动到折叠条可见 | ≤ 1.5 s | 3.0 s |
| PERF-07 | 消息到达 → 界面更新 | ≤ 150 ms | 300 ms |
| PERF-08 | 闪烁期间 CPU 峰值 | ≤ 3% | 5% |
| PERF-09 | 展开/收起主线程阻塞 | ≤ 16 ms | 33 ms |
| PERF-10 | 1000 条消息滚动帧率 | ≥ 55 fps | 45 fps |
| PERF-11 | 拖拽窗口帧率 | ≥ 55 fps | 45 fps |
| PERF-12 | 图片缓存占用 | ≤ 2 GB | — |
| PERF-13 | 数据库体积（1 万条文本） | ≤ 20 MB | 30 MB |
| PERF-14 | 连续 8 小时内存增长 | ≤ 15% | 30% |

**测量方法**：采样前让程序空闲 ≥ 10 分钟；三个时刻各测一次（空闲折叠态 / 展开挂着 / 滚动 1000 条后）；每点连续采样 3 次取中位数；笔记本插电、电源计划"平衡"。

```powershell
# 抽屉全部进程
Get-Process | Where-Object { $_.ProcessName -match 'qq-drawer' -or $_.ProcessName -match 'msedgewebview2' } |
  Select-Object ProcessName, Id, @{n='WS_MB';e={[math]::Round($_.WorkingSet64/1MB,1)}} | Sort-Object WS_MB -Descending
# 官方客户端基线
Get-Process | Where-Object { $_.ProcessName -match 'QQ' } |
  Select-Object ProcessName, Id, @{n='WS_MB';e={[math]::Round($_.WorkingSet64/1MB,1)}}
```

**验收判定**：`PERF-04 实测 ≤ 基线内存合计 ÷ 3` 为优秀；`≤ 基线 ÷ 2` 可接受；高于 `基线 ÷ 2` 需回到优化清单。**PERF-04 超上限 = 不通过**，这是项目核心卖点，不能妥协。（NapCat 是独立上游组件，其占用不计入抽屉预算，但要一并记录以便看清整体成本。）

**优化清单（按收益排序）**

| # | 手段 | 影响 |
| --- | --- | --- |
| 1 | **消息列表虚拟滚动** | 不虚拟化时加载 500 条历史直接把内存拉起来，100 MB 守不住 |
| 2 | **动画只在 CSS 层** | 闪烁只改折叠条自身 `rgba` 与描边，绝不碰窗口 alpha/分层属性 |
| 3 | **窗口几何一次到位** | 折叠↔展开只设一次尺寸，内容动画与之解耦 |
| 4 | **模糊效果只在必要时应用** | 用 `apply_blur`；不在动画中重设 |
| 5 | **图片懒加载 + 本地文件** | 只解码可视区图片，一律读本地 |
| 6 | **成员列表不显示头像** | 几百个头像的网络与解码开销纯浪费 |
| 7 | **无周期性重绘** | 不做跑马灯、不做常驻动画、不做每秒刷新的相对时间（时间分隔用静态文本） |
| 8 | **Rust 侧做重活** | 协议解析、去重、优先级判定全在 Rust |
| 9 | **构建优化** | `lto=true`、`codegen-units=1`、`opt-level="z"`、`strip=true`；不用的 Tauri 特性一律不开 |
| 10 | **SQLite 参数** | WAL + `synchronous=NORMAL`；批量写入用事务；查询命中索引 |
| 11 | **前端按需挂载** | 设置页、缓存管理页只在打开时挂载 |

## 5. 里程碑建议

单人开发。设计原则只有一条：**把"项目可能不成立"的验证放在最前面**，别让写界面制造"项目在推进"的错觉。

| 里程碑 | 主题 | 工期 | 出口条件 |
| --- | --- | --- | --- |
| **M0** | 环境与基线 | 0.5 天 | NapCat 连通（含 token 与上报自身消息）；官方客户端内存基线已记录 |
| **M1** | **数据层验证（Go / No-Go）** | 1–2 天 | 4 个关键接口在本人账号上全部可用；能通过 CLI 收发消息。**不写任何界面** |

| **M4** | 收发与提醒 | 3–4 天 | 能发文本/图片、@ 人；提醒与留痕策略完全符合规范 |
| **M5** | 打磨与验收 | 2–3 天 | 性能验收全部达标；能生成安装包并日常使用 |

```
M0 ──► M1 ──[Go/No-Go]──► M2 ──► M3 ──► M4 ──► M5 ──► v1.0
        │

```

**M1 要验证的 10 件事**：① WS 连接稳定 30 分钟（带 token）；② 打印所有消息事件原始 JSON（含 `message_sent.*`，手机发消息能收到）；③ `get_login_info`/`get_status`；④ **`get_recent_contact` 返回字段形态并定稿适配代码**；⑤ `get_group_msg_history` / `get_friend_msg_history` 分页语义；⑥ `send_group_msg`/`send_private_msg` 真实送达并拿到 `message_id`；⑦ 图片链路（收到 → 下载落盘 → 再用该文件发出去）；⑧ `get_group_member_list`；⑨ 触发一次撤回，确认 `user_id`/`operator_id`/`message_id` 含义；⑩ 断网/停 NapCat 再恢复，确定重连后的补齐范围。

**Go / No-Go 判定**：④⑤⑥⑦ 全部通过 → Go；仅 ⑦ 有问题 → 有条件 Go（先做纯文本版，图片降级占位）；⑤ 或 ⑥ 不通过 → **No-Go，不要开始写界面**，回到方案选型。

**开发约定**：`main` 保持可运行，每个里程碑一条分支；提交信息用 `feat:` / `fix:` / `refactor:` / `docs:` / `perf:` + 一句话（性能相关提交必须附测量数据）；Rust 用 `cargo fmt` + `cargo clippy -D warnings`；纯逻辑（提醒优先级、消息段解析、墓碑过滤、幂等）**必须有单测**，界面走人工走查。

## 6. 已知限制与风险

### 6.1 已知限制（不是 Bug，不要试图"修复"）

1. **读不到也写不了 QQ 自带的免打扰设置**。OneBot 的消息事件里没有该字段；NapCat 群组接口只有 `set_group_ban`（群禁言）、`set_group_remark`、`get_group_detail_info`、`get_group_info_ex`，没有免打扰的读写接口。所以静音只能本地维护——好处是**不可能误改你手机上的设置**。
2. **NapCat 不保存历史**。消息 ID 是哈希生成的正整数，约 5000 条后 LRU 清理，文件标识同样受 LRU 管理，撤回的消息无法再次获取。所以图片必须收到即落盘，**本地缓存是唯一副本**。
3. **掉线期间的事件永久丢失**（含撤回）。掉线时发生的撤回，本地会一直显示为正常消息。不承诺撤回 100% 准确。
4. **无法枚举 QQ 收藏的表情包**——OneBot 没有任何接口能列出收藏夹内容。发送表情包因此不在 MVP 内。
5. **NapCat 在线时电脑端官方 QQ 会被互踢**（符合设计预期；手机端可同时在线）。
6. **Win10 无原生窗口圆角**，圆角为 CSS 绘制。
7. **不嵌入壁纸层**，不置顶时会被其它窗口覆盖。
8. **引用回复只能靠本地缓存的 `message_id`**，不能事后回查（LRU 已清）。

### 6.2 主要风险与应对

| 风险 | 触发信号 | 应对 |
| --- | --- | --- |
| **QQ 账号被风控/限制登录** | 频繁掉线、需重复验证、发送失败 | 见下 §6.3，这是不可消除只能降低的风险 |
| NapCat 掉线频繁 | 一天内多次断开 | 手机 QQ 同时保持在线（社区实测可显著降低掉线率）；显式断线提示 + 自动重连；记录掉线时间分布 |
| QQ 协议升级导致 NapCat 短期失效 | 上游发新版、抽屉连不上 | 协议隔离在 `ob` 层，只需更新 NapCat；不把项目价值绑在某个版本上 |
| NapCat 停止维护 | 上游仓库长期不更新 | 形态 + 交互 + 数据层是自有资产，换协议端只改适配层；必要时退回"只做提醒"的降级形态 |
| 内存超预算 | 实测 > 130 MB | 虚拟滚动、图片懒加载、动画只在 CSS 层；内存合计列为硬判定 |
| 闪烁触发 DWM 重算卡顿 | 每次闪都掉帧 | 闪烁只改折叠条自身 CSS 变量，绝不触碰窗口层 |
| `skipTaskbar` 后窗口丢失 | `Alt+Tab` 找不到 | 托盘常驻 + 全局快捷键 |
| 端口暴露 | 有人扫到本机端口 | 强制 `access_token`；只监听 `127.0.0.1`；**禁止**绑定 `0.0.0.0` 或做端口映射 |
| 数据泄露 | 他人使用本机 | 仅存本机、无遥测、日志不记正文；提供"清空全部本地数据"；明示为明文存储 |

### 6.3 账号风险（最需要正视的一条）

NapCat 是**第三方协议端**，通过逆向 QQ 协议登录，不是官方客户端。使用它违反 QQ 用户协议的相关条款，**存在账号被限制登录、需要验证甚至封禁的可能**。本项目无法消除这个风险，只能降低：

| 做法 | 说明 |
| --- | --- |
| 单账号单设备 | 不做多账号、不做多设备并发 |
| 不写任何自动化 | 不自动回复、不群发、不批量加好友、不自动同意请求 |
| 保持人类使用节奏 | 不做定时任务式高频请求，不轮询拉取 |
| 不爬取不同步不上传 | 数据只落本机 |
| 手机端保持在线 | 符合 NapCat 官方支持的用法，也让登录态看起来更正常 |
| 不修改 QQ 本体 | 不注入、不 Hook 客户端进程 |
| 只在个人设备、个人网络使用 | 不部署公网、不分享给他人 |

**出现风控迹象的处置**：立刻停用抽屉并关闭 NapCat → 用官方客户端/手机端正常登录并做身份验证 → 停用一段时间观察 → 若再次复现则**停止使用本方案**，退回"只在手机上看 QQ"。

> 开始之前先明确：**你能接受的代价是什么？** 如果这个 QQ 号承载了重要的人际关系与资料，那么任何第三方协议端都不该用在这个号上。

## 7. 踩坑清单（实现时逐条对照）

1. **`calc()` 不能放进 `rgba()` 的 alpha 位**——实测完全不生效，背景会整块透明、消息直接穿透。透明度与底色的动态计算必须在 JS/Rust 里算好再写变量。
2. **展开前先取折叠条高度再隐藏它**——先 `display:none` 会测到 0，位置计算全错。
3. **`skipTaskbar` 生效后窗口也从 `Alt+Tab` 消失**——全局快捷键不是可选项。
4. **溢出层不要遮住输入框**——输入区设 `z-index:2`，这样翻会话的同时还能打字。
5. **滚动条必须自定义**——`::-webkit-scrollbar` 宽 6px、`rgba(255,255,255,.12)`、圆角 3px；系统默认样式会破坏透明观感。
6. **文字选中**：消息文本 `user-select:text`，折叠条整体 `user-select:none`（避免拖动时选中文字）。
7. **拖动判定**：位移 > 3px 才算拖动，拖动后要抑制随后的 click（否则一拖就展开）。
   拖动必须走 Rust 的 `begin_drag`（先抑制失焦收起），**不要直接 `startDragging()`**；
   另外标签的 `mousedown` 要 `stopPropagation`，否则"拖标签排序"会同时把整个窗口拖走。
8. **不要用 `apply_acrylic`**：官方文档标注其在 Win10 v1903+ 拖动/缩放时性能很差，而本项目的窗口会被频繁拖动。用 `apply_blur`。
9. **不要在动画中重设 DWM 效果**：每次调用都会重算背景模糊。
10. **不要把状态放前端**：前端可能被重建/刷新，连接、幂等、优先级判定必须在 Rust 侧。
11. **不要做周期性重绘**：跑马灯、每秒刷新的"几分钟前"都会让空闲 CPU 永不归零。时间分隔用静态文本。
12. **成员列表不要加载头像**：几百个头像的网络与解码开销纯浪费。
13. **虚拟滚动的视口位置只能由锚点派生**：`offsets` 换代（行高测量回填 / 翻页插入）后，
    先取锚点（行 id + 行内偏移）再反算 `scrollTop`，**不要写"把新插入的高度加到 scrollTop 上"**
    这类增量补偿——增量里混着测量、图片撑开、占位高度变化，补出来的位置是错的。
    未测行的估值取已测行高的中位数，不要用固定值。还有一串连带的坑，每一个都单独能让滚动抽风：
    ① `ResizeObserver` 要在组件函数体里创建，**不能等 `onMount`**——JSX 的 `ref` 回调比
    `onMount` 先跑，在 `onMount` 里建会导致首屏的行一个都没被观察，高度一直停在估值上，
    用户一开始滚动才补测，那一瞬间的抖动最猛；
    ② 贴底跟随只能由「向下追加」触发（比较行序首元素），翻页前插时跟到底部就成了
    「往上翻一页被弹回底部」的鬼打墙；
    ③ **估值只学一次**：它参与 `padTop` / `padBottom`，跟着每个新样本重算的话**所有未渲染行**
    会一起浮动 —— 500 行列表里是几千像素的 `scrollHeight` 突变，滚动条长度跟着跳，
    渲染窗口边界大幅移动又引发新一波测量，自激之下滚轮直接不动了；
    ④ **行对象要复用引用**（`createRowCache`）：`<For>` 按引用 diff，行对象每次全新的话，
    一次消息追加就把整个渲染窗口（约 30 个节点）的 DOM 全部销毁重建，连带 30 次 `ref` 回调、
    30 次首测、一轮行高回填，回填又改写坐标系触发下一轮 —— 同上，自激。
    注意 `separator` 是**对象**，判定"没变"要逐字段比，直接 `===` 会恒为 false 让缓存静默失效；
    ⑤ 程序补偿写入的 `scrollTop` 必须与用户的滚动**区分开**（浏览器派发的 scroll 事件里分不出
    这两者）：不区分的话补偿会被当成"用户滚到底了"，重新打开贴底跟随；同样地，翻页等待期间
    也要挂起贴底态的重算，否则用户那几下滚动会把刚设的 `false` 冲掉。贴底阈值还要收得很紧
    （12px），太松的话用户往上滚二三十像素仍被算作贴底，紧接着的行高回填就把他拽回最底部；
    ⑥ 行间距做在 `.row-wrap` 的 `padding-bottom` 上，**不要用父级 flex `gap`**（`gap` 不计入
    `offsetHeight`）；「以上是全部」这类提示条要用绝对定位浮层，**不能占布局高度**——
    它们进进出出会改变 `scrollHeight`，而它们不在行高测量的观察范围内，没人替视口补偏移。
